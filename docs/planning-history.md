# Veyro — Planning History

A chronological log of key decisions made during planning. Reference this to understand *why* a decision was made, not just what it is — later docs (architecture, schema, etc.) reflect the end state; this doc preserves the reasoning trail.

## Business Model
- Decided Veyro is a direct-buy model (users sell to Veyro, Veyro liquidates) — not a peer-to-peer marketplace or escrow platform. This shapes accounting (ledger-based), liquidity ownership, and fraud responsibility.

## Rate Sourcing
- Investigated multiple gift card rate/liquidation APIs: Reloadly (signup blocked from Nigeria — rejected, including a VPN workaround which was assessed and rejected due to KYB exposure and ToS risk), Cardtonic (waitlist-only, not usable yet), Sogo (developer API publicly listed as "in the works," not available), Giftbit (confirmed wrong category — issuing/rewards API, not liquidation/rate data).
- Prestmit confirmed as the viable option — Nigeria-native, real documented sandbox/application process. Application submitted, pending approval.
- Decision: V1 launches with manually-set "Platform Rates," structured so the rate source is pluggable — live API can be swapped in later without rebuilding frontend or schema.
- A ChatGPT-sourced document referencing a detailed Prestmit Partner API (with a specific endpoint and documentation titled "How To Make Money Using Prestmit API") was flagged as unverified — those specifics should be confirmed directly in Prestmit's docs once sandbox access is granted, not assumed from secondhand summary.

## Crypto Scope
- Initially recommended deferring crypto to a later phase (to avoid overlap with Monance and reduce V1 compliance/build scope).
- Decision reversed: crypto included in V1 from the start, to avoid building the wallet/verification/payout pipeline twice.
- Custody model simplified from Monance's per-user HD wallet approach: Veyro will publish static deposit addresses; users send crypto and submit proof of deposit; admin manually confirms before payout (P2P-style, no per-user address generation, no custody infrastructure).
- Crypto price feed: reusing Monance's existing CoinGecko REST + Binance WebSocket integration rather than sourcing a new one.

## Branding
- App named Veyro.
- Deliberately chose a light theme, distinct from Monance's dark Binance-style theme, to read as a separate, distinct product.
- Avoided green as primary accent (overused in fintech/crypto, and CashApp/most competitors already use it) — landed on terracotta/coral (`#E8674A`) with an off-white background, deep charcoal-navy text, muted sage for success states, and Space Grotesk headers paired with Inter/General Sans body text.

## Tech Stack
- Evaluated fresh for Veyro's actual requirements rather than defaulting to prior project stacks.
- Landed on: Next.js + Tailwind + shadcn/ui (Vercel) for frontend, NestJS on GCP Cloud Run for backend, Supabase for DB/Auth/Storage — matching Monance's backend hosting (GCP) to avoid new infra accounts.
- Originally considered a crypto payment processor (Coinbase Commerce/BitPay) to avoid building custody — made moot once the manual deposit-address model was chosen instead.
- Payment gateway integration (Paystack/Flutterwave) considered for automated payouts, then explicitly ruled out for V1 — payouts (bank transfer, PayPal, crypto) are handled manually by admin instead.
- Paid KYC (Sumsub) considered, then deferred to Phase 2 — V1 relies on manual admin judgment per trade, functioning as the fraud check given every trade is reviewed anyway.

## Crypto Custody (Tatum Integration)
- Confirmed via Tatum's docs that all 7 listed assets (BTC, ETH, USDT, BNB, SOL, XRP, DOGE) are supported chains, resolving the earlier-unresolved question of whether XRP and Dogecoin specifically were covered.
- XRP turned out to need a different addressing model than the other 6: Tatum does not support a unique on-chain address per user for XRP (freezing a reserve for every generated address is prohibitively expensive on the XRP Ledger). Tatum's documented pattern instead is one shared platform address for all users, with a `destination_tag` distinguishing each user's deposits. `user_crypto_addresses` was extended with a nullable `destination_tag` column for this rather than forcing XRP into the same derived-unique-address shape as the other chains.
- Key-handling plan: one master mnemonic/seed per chain (7 total; XRP's "master" is really just one funded address + its private key, not an HD tree), generated via Tatum's own SDK generation flow rather than an ad-hoc script, written only to GCP Secret Manager (never `.env`, never committed, never a persisted log). Only the resulting xpub is loaded into the running API day-to-day (BTC/ETH/BSC/TRON/SOL/DOGE) — that's all `generateAddressFromXpub` needs, and it's safe to hold since it can't sign anything. The master seed itself is touched once at setup to derive that xpub, then never read again in normal operation.
- XRP's private key is the one exception to "the always-running API can reach what it needs": since day-to-day XRP address handling never touches the private key (only actual outbound fund movement does), its Secret Manager IAM is deliberately scoped tighter than the other 6 chains' — the main API service account has no access to it at all. It sits behind a separate, deliberately-invoked path (a distinct service account or manual process), used only when an actual XRP payout is being executed.
- Solana flagged as a genuine open question, not yet resolved: Tatum's own docs are ambiguous about whether Solana supports true xpub+index derivation the same way BTC/ETH/TRON/DOGE do, or whether each Solana address needs its own generated keypair instead (their generateWallet docs say "only one address generated per mnemonic"). The address-generation service assumes the xpub+index shape for now (config key `TATUM_SOL_XPUB`) but this needs verifying against Tatum's actual API response before the Solana path is relied on in production.
- No per-user address is pre-generated. `user_crypto_addresses` rows are created lazily, service role only, the first time a user needs one (Deposit Crypto or Sell Crypto for that asset).

## Sweeper (Cloud Run Job)
- Expanded the supported coin list from 7 to the 20 Tier 1/2 coins (BTC, ETH, USDT, BNB, XRP, DOGE, POL, AVAX, CELO, FLR, FTM, CRO, ETC, KAIA, XDC, LTC, BCH, XLM, USDC, TRX) - deliberately not padded to 25 with Tier 3 chains. Arbitrum/Optimism/Base are additional network options under ETH/USDT/USDC, not separate top-level coins, since they're EVM L2s sharing the same address space as their L1. SOL was dropped (was never a confirmed xpub-derivation chain per the earlier Crypto Custody note, and isn't part of the 20-coin list) - its existing rows are deactivated, not deleted.
- 7 master seeds map onto 20 coins as: 4 dedicated UTXO xpubs (BTC, LTC, BCH, DOGE) + 1 shared EVM xpub (covers all 11 EVM chains plus Arbitrum/Optimism/Base - one private key produces the identical address across every EVM-compatible chain, that's inherent to the technology, so splitting per-EVM-chain would add operational complexity with no real isolation gain) + 1 TRON xpub (TRX + USDT/USDC-TRC20) + 1 combined XRP+XLM secret (both are non-HD, shared-single-account chains like today's XRP, grouped under one Secret Manager entry as an organizational convenience - not a claim their key material is related, they use different signing algorithms and stay cryptographically distinct within that one JSON blob).
- Built as a genuinely separate deployable (`apps/sweeper`), not a module inside `apps/api`: its own Dockerfile, its own Cloud Run **Job** (not service - runs to completion and exits per invocation), its own dedicated service account, its own CI workflow (`sweeper-deploy.yml`), triggered only by `apps/sweeper/**` changes.
- IAM: the sweeper's service account is the ONLY identity with `secretAccessor` on the 7 master seeds; the main API's runtime service account is explicitly denied on all 7 (generalizing the XRP-only precedent from the Crypto Custody section to every chain) - `apps/sweeper/scripts/gcp/bootstrap-sweeper-iam.sh` sets this up, run by hand once, not by CI.
- Schedule: two Cloud Scheduler jobs invoke the same image with a different `SWEEP_GROUP` env var - 12h for UTXO chains (BTC/LTC/BCH/DOGE), 6h for everything else (every EVM chain, plus TRON/XRP/XLM, which behave operationally like EVM chains - fast finality, low fees, no UTXO consolidation needed - even though they aren't EVM-compatible themselves).
- Sweeps into a dedicated, non-HD `consolidation_wallets` row per chain, never into any address in the user-facing HD derivation tree - deliberately separate custody paths for "where deposits land" vs "where swept funds live."
- Fee-aware minimum thresholds live in `platform_settings` (`sweep_min_threshold_*` keys), not hardcoded, so an admin can retune a chain's minimum without a redeploy.
- `sweep_log` is an append-only audit trail, one row per sweep attempt (not per run), service-role-only - no client policy, not readable by the API's runtime service account.
- Real master seed material is deliberately NOT generated as part of this build - the secrets are created empty by the bootstrap script; populating them with actual seeds is a separate, explicit, later step (see apps/sweeper/README.md), same handling discipline as the original Crypto Custody plan (seeds touched once at setup, held only in Secret Manager, never in a running process's env vars or logs).
- Flagged as needing dedicated testnet verification before any production use: the exact BIP44 derivation path each chain adapter uses (must match whatever path Tatum used to derive the xpubs `apps/api` already holds, or the sweeper will compute a different address than users actually deposited to), every hardcoded token contract address, and Bitcoin Cash's SIGHASH_FORKID transaction construction specifically (thinnest Tatum coverage, highest implementation risk of the chains covered).
- XRP and Stellar dropped from the supported coin list entirely (20 Tier 1/2 coins → 18), at the point of actually generating the real master seed material for the first time. Checking Tatum's current docs (their SDK has restructured since the original Crypto Custody note above was written) surfaced that neither chain has a local-mnemonic wallet-provider at all: Tatum generates their keypairs server-side via a REST call (`GET /v3/xrp/account`, `GET /v3/xlm/account`), a materially different trust model than the other 6 chains, which generate entirely locally via the SDK's per-chain wallet-provider packages before ever touching Secret Manager. Standing rule going forward: a coin whose integration creates friction or a different trust model than the rest gets suggested for removal rather than worked around inline - V2 can revisit XRP/XLM properly (e.g. sourcing their keys from a local, non-Tatum library instead) if there's real demand. `SWEEPER_XRP_XLM_SEED` (the combined secret the original 7-secret plan allocated to them) is removed from scope entirely, leaving 6 master seed secrets. The generic shared-address/destination-tag mechanism (`user_crypto_addresses.destination_tag`, `ChainConfig.derivationStyle: 'shared-tag'`) was kept rather than ripped out, since it isn't XRP/XLM-specific and is exactly what a future shared-address chain would reuse.
- Bitcoin Cash dropped too, immediately after (18 → 17), for the identical reason: generating its real seed threw `Extension UtxoWalletProvider is not supported on bitcoin-cash-mainnet network` on the first attempt. Checked directly against `@tatumio/utxo-wallet-provider`'s actual source (`tatumio/ecosystem-addons`, not just its marketing docs page, which incorrectly claims BCH support) - its `NETWORK_CONFIG`/`DERIVATION_PATHS` maps only cover `Network.BITCOIN`, `Network.LITECOIN`, `Network.DOGECOIN` (+ testnets), and there is no dedicated BCH wallet-provider package the way TRON/EVM each got one. The only Tatum path to a BCH mnemonic is `GET /v3/bcash/wallet`, a server-side REST generation - same trust-model mismatch as XRP/XLM, so the same standing rule applied. `SWEEPER_BCH_SEED` (created empty by an earlier version of `bootstrap-sweeper-iam.sh`, never populated - generation failed before writing anything, confirmed via `gcloud secrets versions list` showing 0 items) is removed from the script's `SECRETS` array; the empty GCP secret container itself was left in place, not deleted, pending a manual `gcloud secrets delete` if wanted. Final count: **5 master seed secrets, all generated and verified** (BTC, LTC, DOGE, EVM covering ETH + every EVM chain, TRON), covering **17 Tier 1/2 coins**.
- USDC-TRC20 dropped as a network option too (17 coins unchanged - this drops one network variant of an already-supported coin, not a whole coin), discovered while verifying the sweeper's hardcoded TRC20 contract addresses before deployment: Tronscan's own API tags `TEkxiTehnzSmSe2XqrBj4w32RUN966rdz8` (the address this codebase had hardcoded) as `name: "USD Coin Old", symbol: "USDCOLD"` - not current USDC. Cross-checked against Circle's own blog: Circle announced in February 2024 that it was discontinuing USDC support on TRON entirely, phase-out complete by February 2025 - there is no current Circle-issued USDC-TRC20 contract to substitute in its place. USDT-TRC20 was verified genuine in the same pass (Tronscan: "Tether USD", ~$40B/24h volume, 76M holders) and stays. USDC remains supported on ERC20/Arbitrum/Optimism/Base, all unaffected. No `crypto_assets` migration was needed for this one - a live DB check found no USDC/TRC20 row had ever actually been seeded, only the frontend/API config offered it as an option.
- Separately (and this is the reason the Deposit Crypto page was showing empty): all 6 `TATUM_*_XPUB` env vars in `apps/api/.env` turned out to be genuinely blank - the 5 real master seeds existed in Secret Manager, but the separate step of deriving their xpubs and populating `apps/api`'s config had never actually happened. Not a regression, a missing step never done in the first place.

## Public Site Structure
- Original plan (from earlier ChatGPT planning): Home, Gift Cards, Rates, How It Works, About, FAQ, Contact, Legal — plus a dedicated public Crypto page added later for separate SEO/trust content from gift cards.
- Revised and finalized: nav simplified to a single card-tile dropdown menu with Gift Cards, Crypto, FAQ, Contact Us, plus Log In / Get Started. How It Works dropped (homepage already covers it), Rates dropped as a standalone page (folded into Gift Cards and Crypto pages instead), About dropped. Legal pages remain, footer-only.
- Along the way, a dedicated public Crypto page was initially left out of nav planning despite being decided on earlier — caught and corrected.
- Authenticated app: Dashboard, Sell (shared flow with Gift Card/Crypto toggle), Transactions, Wallet, Referrals, Leaderboard, Settings, Support.
