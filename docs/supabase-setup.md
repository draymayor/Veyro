# Veyro — Supabase Setup

## Project Setup

1. Create a new Supabase project dedicated to Veyro (separate from Monance's project — no data or auth sharing between the two products).
2. Region: choose based on primary early user base — given Nigeria-first launch expectations, an EU or US-East region is typically closest/cheapest; confirm against actual latency needs once traffic patterns are known.
3. Enable Auth providers: email/password at minimum for V1. Social login (Google) optional, not required for launch.

## Auth Configuration

- Use Supabase Auth's built-in `auth.users` table; extend with a `public.users` profile table (see `database-schema.md`) linked 1:1 via `id`.
- Country selected at signup triggers a Postgres trigger or backend hook to set `currency` on the profile row.
- Session handling: NestJS backend verifies Supabase JWTs on incoming requests (standard Supabase server-side auth pattern).

## Storage Buckets

- `card-images` — gift card photo uploads (private bucket, admin + owning user access only)
- `receipts` — proof-of-purchase receipts where required (private)
- `deposit-proofs` — crypto proof-of-deposit screenshots (private)

All buckets private by default; access via signed URLs generated by the backend, never public bucket URLs — these images can contain sensitive card codes or transaction details.

## Row-Level Security (RLS)

Enable RLS on all user-facing tables. Baseline policies:

- `trades`: `user_id = auth.uid()` for SELECT; INSERT allowed for authenticated users creating their own trade; UPDATE restricted to backend service role only (status transitions happen server-side, not client-side).
- `wallets`, `wallet_transactions`: SELECT restricted to `user_id = auth.uid()`; no client-side INSERT/UPDATE at all — these are backend-service-role-only writes, enforced via ledger rules in `product-rules.md`.
- `withdrawals`: SELECT restricted to own records; INSERT allowed for authenticated users (requesting a withdrawal); UPDATE restricted to service role (admin processing).
- `gift_card_rates`, `crypto_assets`: public SELECT (needed for the public rates page and live sell-flow quoting); INSERT/UPDATE restricted to admin role only.
- `admin_actions`: no client access at all; service-role/backend-only.

## Admin Role

- Implement via a `role` claim on the Supabase user (custom JWT claim or a separate `admin_users` table checked server-side) rather than relying on RLS alone for admin actions — sensitive actions (approve/reject trades, edit rates, process withdrawals) should route through NestJS backend endpoints that verify admin role server-side, not direct Supabase client calls.

## Migrations

- Use Supabase CLI migrations (`supabase migration new`) checked into the repo under `supabase/migrations/` — mirrors the schema in `database-schema.md`.
- No manual schema edits via the dashboard for anything beyond local prototyping — all schema changes should be captured as migration files for reproducibility.

## Environment Variables (backend)

```
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=      # backend only, never exposed to frontend
SUPABASE_ANON_KEY=              # frontend-safe
```

## What's Explicitly Not Set Up in V1

- No Supabase Edge Functions dependency planned — background/webhook logic lives in the NestJS backend on Cloud Run instead, per `architecture.md`.
- No automated KYC provider webhook integration (deferred to Phase 2 per `roadmap.md`).
- No payment gateway webhook integration (Paystack/Flutterwave) — payouts are manual in V1.
